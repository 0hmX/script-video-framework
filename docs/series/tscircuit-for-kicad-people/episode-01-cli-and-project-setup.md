# tscircuit for KiCad People

## Episode 1 — Install the CLI, Understand the Commands, and Set Up a Project

Status: review draft 1  
Target runtime: 50–65 minutes  
Teaching mode: manual-first, no AI required  
Episode boundary: stop after the starter project has been initialized, inspected, and verified

## Series promise

This series teaches tscircuit to people who already think in KiCad terms. It does not assume that the viewer is a TypeScript developer, and it does not hide the workflow behind an AI prompt. Every important file, command, input, and output is explained directly.

AI appears only in clearly marked sidebars. The manual workflow remains the main path, and everything shown in an AI sidebar must still be inspectable and reproducible without AI.

## What Episode 1 must accomplish

By the end of this episode, the viewer should be able to answer five questions:

1. What is tscircuit, and how is its source-first model different from KiCad's editor-first model?
2. What are Bun, `tscircuit`, and the `tsci` command?
3. How do I install and verify the CLI without guessing whether it worked?
4. What does every major `tsci` command family do?
5. What files does `tsci init` create, and why does each file exist?

The viewer will not design a circuit in this episode. The generated starter circuit can be opened and read, but editing it belongs to Episode 2.

## 00:00 — Opening: this is not “AI makes a PCB”

### Narration

If you come from KiCad, you probably expect an electronics project to begin with a project manager, a schematic editor, a symbol library, a footprint assignment step, and eventually a PCB editor. You click, place, wire, inspect, and save. The project is represented by a collection of files, but most of your intent is entered through graphical tools.

tscircuit begins from a different direction. The primary design input is source code. Components, connections, schematic placement, PCB placement, and other design intent can be expressed in TypeScript and JSX. The toolchain evaluates that source and produces a shared representation called Circuit JSON. Schematic, PCB, 3D, simulation, validation, and manufacturing-oriented outputs are built from that representation.

That does not mean we type one vague sentence into a chatbot and trust whatever comes back. This series is deliberately manual. We will install the tools ourselves, read the generated files, write the circuit ourselves, run the checks ourselves, and inspect the outputs ourselves.

AI can help, and I will show what it can do in a small side lane. But AI is not the foundation of the workflow. The source code, the compiler output, and the engineering checks are the foundation.

In this first episode, we are going slowly. We will install the command-line interface, understand its commands, initialize a project, inspect every generated file, and stop there. We will not rush into placing components before the project underneath them makes sense.

### Host checkpoint

## 03:30 — The mental model for a KiCad user

### Narration

Before installing anything, let us establish a translation layer between KiCad and tscircuit.

In KiCad, the project file and the editor applications organize the work. In tscircuit, a normal project is also a directory, but its center of gravity is a TypeScript circuit entry file, usually named `index.circuit.tsx`, plus ordinary package and compiler configuration.

In KiCad, adding a symbol to the schematic creates an object inside a schematic document. In tscircuit, a component can be declared as an element in source code. A resistor, for example, is represented by a resistor element with properties such as its name, resistance, and footprint.

In KiCad, a wire joins pins in the schematic. In tscircuit, connectivity can be expressed with traces and named nets. The exact syntax will be the subject of the next episode. For now, the important point is that the connection is readable as text and can be reviewed in a normal source diff.

In KiCad, footprints, board placement, routing, and fabrication outputs live in later stages of the graphical workflow. tscircuit can derive multiple views and outputs from the same source and Circuit JSON representation. Some work can be automated, but automated does not mean uninspectable. You can run focused checks and export concrete artifacts.

Here is the most useful simplified pipeline to remember:

```text
TypeScript / JSX source
        ↓
tscircuit evaluation
        ↓
Circuit JSON
        ↓
schematic · PCB · 3D · checks · exports
```

Circuit JSON is not something we need to hand-author today. Think of it as the shared design boundary generated by the toolchain. It is useful because different tools can agree on the same circuit data instead of each view becoming an unrelated drawing.

### KiCad-to-tscircuit translation table

| KiCad idea | Closest tscircuit idea | Important difference |
|---|---|---|
| KiCad project directory | tscircuit package directory | It also behaves like a TypeScript package |
| `.kicad_sch` schematic | `index.circuit.tsx` plus generated schematic view | Source code is the primary authored input |
| Symbol properties | JSX element properties | Properties are typed and diffable |
| Wires and net labels | `<trace />` declarations and named nets | Connectivity is expressed in source |
| Footprint assignment | `footprint` properties or component packages | Selection can be declared with the component |
| ERC and DRC | `tsci check ...` command family | Checks can be run separately from the editor |
| PCB editor and router | PCB properties, constraints, and routing pipeline | More of the process can be automated from source |
| Plot/export dialogs | `tsci build` and `tsci export` | Outputs can be scripted and repeated |

### Important qualification

Do not claim that tscircuit is “KiCad in text form.” That is too simplistic. The tools have different architectures and different strengths. The goal of this series is to give KiCad users enough familiar reference points to learn the new model without pretending the models are identical.

## 09:00 — What we are installing

### Narration

There are two names that can be confusing at first.

`tscircuit` is the package and the broader electronics toolchain. `tsci` is the command installed by that package. We install `tscircuit`, but most terminal commands begin with `tsci`.

The official installation guide supports npm or Bun and recommends Bun for speed and ease of use. This series will use Bun consistently. Mixing package managers inside one project creates avoidable confusion around lockfiles and dependency state, so every package command in this series will use Bun.

Bun is a JavaScript and TypeScript runtime and package manager. You do not need to become a Bun expert today. For this episode, we need it to do three jobs:

1. install the tscircuit CLI;
2. install project dependencies;
3. run scripts declared by the generated project.

### Terminal preflight

Run these commands one at a time:

```sh
echo $SHELL
pwd
bun --version
```

### Narration

`echo $SHELL` tells us which command shell the account is configured to use. On modern macOS, this will commonly be zsh. On Linux it may be bash, zsh, or something else. This matters when an installer tells us to update a shell configuration file.

`pwd` prints the current working directory. A command-line workflow is always operating somewhere. Before creating or modifying a project, get into the habit of checking where you are.

`bun --version` asks the shell to find Bun on the executable search path and run it. If it prints a version, Bun is installed and discoverable. If it prints “command not found,” do not continue to the tscircuit installation yet. Fix Bun first.

## 13:00 — Install Bun if it is missing

### Narration

If Bun is already installed, skip this chapter. If it is missing, use the current command from Bun's official installation page rather than copying a random command from an old video description.

At the time this script was researched, the official macOS and Linux installer command is:

```sh
curl -fsSL https://bun.com/install | bash
```

On Windows PowerShell, the official command is:

```powershell
powershell -c "irm bun.sh/install.ps1|iex"
```

### Narration

Let us unpack the macOS and Linux command rather than treating it like magic.

`curl` retrieves data from a URL. The flags make it fail clearly on HTTP errors, avoid unnecessary progress output, still show useful errors, and follow redirects. The pipe sends the downloaded installer to `bash`.

Any command that downloads code and executes it deserves scrutiny. The safe habit is to obtain it from the official project documentation, confirm the domain, and review the installer if your environment requires that level of control. Package-manager alternatives such as Homebrew are also documented by Bun.

After installation, close and reopen the terminal, then run:

```sh
bun --version
bun --revision
```

The version identifies the release. The revision identifies the precise Bun build. We do not need to memorize either value. We need to establish that the executable works.

### PATH troubleshooting

If the installer succeeded but `bun` is still not found, the likely issue is the `PATH` environment variable. `PATH` is the ordered list of directories the shell searches for commands.

For zsh, Bun's documentation shows adding the Bun binary directory to `~/.zshrc`:

```sh
export BUN_INSTALL="$HOME/.bun"
export PATH="$BUN_INSTALL/bin:$PATH"
```

Then reload the shell configuration:

```sh
source ~/.zshrc
bun --version
```

Do not keep reinstalling Bun if the binary exists and the real problem is `PATH`.

## 19:00 — Install the tscircuit CLI

### Narration

With Bun working, install tscircuit globally:

```sh
bun install --global tscircuit
```

“Global” means the command is installed for your user environment rather than added to one project's dependency list. This gives us the `tsci` command we need to create projects.

Now verify the installation with three separate checks:

```sh
command -v tsci
tsci version
tsci doctor
```

### Narration

`command -v tsci` asks the shell which executable will run when we type `tsci`. This is useful when several installations exist or when an old executable appears earlier in `PATH`.

`tsci version` proves that the executable starts and tells us which CLI release is active. For a detailed environment report, use:

```sh
tsci version --verbose
```

`tsci doctor` runs diagnostic checks for the tscircuit setup. A version number alone only proves the command can start. Doctor is the better first stop when the environment behaves strangely.

Finally, print the help page:

```sh
tsci --help
```

Do not skim past this. The help output is the installed CLI describing itself. Documentation can lag a release; the local help output tells us which commands this machine can actually run.

### Global versus project-local installation

The documentation also supports installing tscircuit as a project development dependency:

```sh
bun add --dev tscircuit
```

The global CLI is convenient for `tsci init`. A project-local dependency makes the project's expected tool version explicit in `package.json` and lockfile state. The generated project includes tscircuit as a development dependency, so collaborators can restore it with the project dependencies.

These are not mutually exclusive. It is common to have a global command for bootstrapping and a local dependency recorded by each project.

## 25:00 — How to read a CLI command

### Narration

Before touring the command list, let us read one command structurally:

```sh
tsci init [options] [directory]
```

`tsci` is the executable. `init` is a command. Items in square brackets are optional. The word `directory` is a positional argument: its meaning comes from its position. Options begin with a dash, such as `--no-install` or the short form `-y`.

For any command, ask for its focused help:

```sh
tsci help init
```

or:

```sh
tsci init --help
```

Both forms are useful. This habit is more important than memorizing flags.

Some commands contain another level. For example:

```sh
tsci check shorts --help
```

Here, `check` is the command family and `shorts` is the nested command. The final `--help` asks specifically about short-circuit detection.

## 29:00 — The complete CLI map

### Narration

The goal of this chapter is orientation, not memorization. We will group commands by job. When a command belongs to a later episode, I will say so instead of pretending we need it today.

### Group 1: begin, run, diagnose, and learn

#### `tsci init [directory]`

Creates a new tscircuit project in a named directory or in the current directory. Its important options are:

```text
-y, --yes     use defaults and skip prompts
--no-install  create files without installing dependencies
```

We will use the interactive form today because seeing the prompts teaches us what is being decided.

#### `tsci dev [file]`

Starts the local development server. The default port is `3020`. The official quickstart explains that the browser can show PCB, schematic, and 3D views and rebuild as source changes. We will start using `dev` in Episode 2, after we understand the starter source.

Useful help includes a custom `--port` and autorouter diagnostic options. Do not add debug flags by default; use them when diagnosing a routing problem.

#### `tsci doctor`

Runs setup diagnostics. Use this before randomly reinstalling tools.

#### `tsci version`

Prints the CLI version. `tsci version --verbose` prints tscircuit and CLI dependency versions as well.

#### `tsci help [command]`

Shows general help or focused command help. This is the command that keeps the tutorial useful even as new options are added.

### Group 2: compile, inspect, and validate

#### `tsci build [file]`

Evaluates the circuit and writes Circuit JSON and requested artifacts. The command can generate PCB, schematic, and 3D images; SVGs; static sites; KiCad projects; GLB or STEP models; and debugging artifacts. Build is broad because it drives many deterministic outputs.

We are not using all of those flags today. The important distinction is that `build` produces artifacts, while `dev` runs an interactive development loop.

#### `tsci transpile [file]`

Transpiles TypeScript and TSX into JavaScript and type declarations. This is a software packaging operation, not the same as compiling a circuit into Circuit JSON.

#### `tsci snapshot [path]`

Generates reference snapshots for schematic and PCB output, with options for 3D, one PCB layer, or focused view types. Snapshot testing is valuable for detecting unintended design changes in a code review or continuous-integration system.

#### `tsci check`

Runs focused validation stages. Its current nested commands are:

```text
tsci check netlist
tsci check pin_specification
tsci check placement
tsci check routing-difficulty
tsci check schematic-placement
tsci check shorts
tsci check source
tsci check trace-length
```

Here is the conceptual order to remember for future episodes:

1. `source` catches source-level diagnostics.
2. `netlist` verifies electrical connectivity.
3. `pin_specification` checks pin definitions.
4. `schematic-placement` checks schematic readability and collisions.
5. `placement` checks physical PCB placement.
6. `routing-difficulty` estimates routing trouble before wasting time.
7. `trace-length` measures a selected pin or net path.
8. `shorts` detects unintended copper connections, using Gerber-derived analysis by default.

That separation will feel familiar to a KiCad user who distinguishes ERC, placement review, routing review, and DRC, even though the exact models are not identical.

### Group 3: export and interoperability

#### `tsci export <file>`

Exports a circuit to a selected format and path. Current formats include Circuit JSON, schematic SVG or PDF, PCB SVG, Gerbers, readable netlists, GLTF or GLB, Specctra DSN, KiCad schematic or PCB formats, KiCad ZIP and library outputs, STEP, assembly SVG, and more.

The basic shape is:

```sh
tsci export index.circuit.tsx --format pcb-svg --output board.svg
```

We will cover manufacturing exports in a later episode. Do not imply that merely producing a Gerber archive proves electrical correctness or manufacturability.

#### `tsci convert <file>`

Converts a `.kicad_mod` footprint to TSX, or attempts to identify an equivalent footprinter string. This is especially relevant to KiCad users carrying footprint work into the tscircuit ecosystem.

#### `tsci setup`

Sets up project utilities such as GitHub Actions support. We will use it only when we reach automation and continuous integration.

### Group 4: components and dependencies

#### `tsci search <query...>`

Searches the tscircuit ecosystem. The installed CLI currently exposes focused search flags for KiCad footprints, JLCPCB components, and tscircuit registry packages, plus JSON output for scripts.

#### `tsci import <query...>`

Searches JLCPCB or the tscircuit registry and imports a component. Options can download 3D model assets or preserve an exact EasyEDA footprint instead of using a close footprinter match.

Search answers “what exists?” Import brings a selected component into the project. Do not collapse those into one idea.

#### `tsci add <package...>`

Adds one or more tscircuit component packages to the project. Package specifications can include a registry name, author/component form, GitHub URL, or version.

#### `tsci remove <component>`

Removes a component package from the project.

#### `tsci install [package]`

With no package argument, installs the project's dependencies. With a package or supported URL, installs that package. This is distinct from the first global `bun install --global tscircuit` command: one installs the CLI for the user; the other operates on a tscircuit project.

#### `tsci update [package]`

Updates one selected tscircuit component package, or all `@tsci` dependencies when no package is supplied.

#### `tsci upgrade`

Upgrades the CLI itself. Version-control your project and read release notes before changing important tool versions in production work.

#### `tsci clone [package]`

Clones a package from the tscircuit registry, including packages identified by registry URL. It can also clone a bug-report project for reproduction and debugging.

### Group 5: identity, configuration, and registry operations

#### `tsci auth`

The authentication family contains:

```text
tsci auth login
tsci auth logout
tsci auth whoami
tsci auth print-token
tsci auth set-token <token>
tsci auth setup-npmrc
```

Top-level `tsci login` and `tsci logout` also exist as convenient commands.

Never display `print-token` output in a recording, screenshot, issue, or live stream. Authentication tokens are credentials.

#### `tsci config`

`tsci config print` shows current configuration. `tsci config set <key> <value>` changes a configuration value. Before changing a setting, print the current configuration and understand whether the setting is global or project-specific.

#### `tsci push [file]`

Publishes project code to the tscircuit registry. It supports private packages, version tags, optional `dist` inclusion, and compressed upload. This changes remote state. We will not run it casually in a setup episode.

#### `tsci registry packages`

The registry package family currently provides `create` and `update` nested commands for managing package resources. These are administrative operations, not required for a local first project.

### Group 6: simulation and AI

#### `tsci simulate analog <file>`

Runs an analog SPICE simulation for tscircuit TSX or Circuit JSON input. Simulation deserves its own later episode because a successful simulation depends on models, sources, analysis configuration, and correct interpretation.

#### `tsci agent [args...]`

Installs or invokes the separate `tsci-agent` workflow. This is the optional AI lane. The manual command set does not depend on it, and we will not install or run it in the main path of Episode 1.

### End-of-map reminder

Do not memorize this list. Remember the groups and use help:

```sh
tsci --help
tsci <command> --help
tsci <command> <subcommand> --help
```

## 43:00 — Optional AI sidebar: where AI belongs

### Narration

Here is the narrow role AI will play in this series.

An AI assistant can explain unfamiliar terminal output, draft repetitive component declarations, suggest a debugging sequence, or help search a large source tree. It can make a knowledgeable operator faster.

It cannot turn an unchecked circuit into a trustworthy circuit. It can invent a property, choose the wrong pin, misunderstand a footprint, or propose a command that belongs to another CLI version. That is why every AI-assisted change must return to the same manual loop:

```text
read the source
inspect the diff
run the focused checks
inspect the generated result
```

For this episode, we will decline the optional AI-skill setup during initialization. That proves the project and CLI stand on their own. Later, we can repeat a small task with AI in a side panel and compare the result against the manual process.

### Sidebar rule for the whole series

Never let AI activity cover the main terminal or replace an explanation. The viewer should always know which command ran, which file changed, and how the result was verified.

## 46:00 — Initialize the first project manually

### Narration

We are ready to create the project. First choose a parent directory where electronics projects belong. I will use a directory named `Documents/tscircuits`, but use a location that makes sense on your machine.

Run each command separately:

```sh
mkdir -p ~/Documents/tscircuits
cd ~/Documents/tscircuits
pwd
```

`mkdir -p` creates the directory if it does not exist and avoids failing if it already exists. `cd` changes the terminal's working directory. `pwd` confirms where the next command will operate.

Now create and enter an empty project directory:

```sh
mkdir kicad-people-demo
cd kicad-people-demo
pwd
ls -la
```

The final `ls -la` should show that the directory is empty apart from `.` and `..`. This prevents accidentally initializing over unrelated work.

Run the initializer interactively:

```sh
tsci init
```

### Prompt walkthrough

The precise wording can change between CLI releases, so read the prompts on screen rather than pressing Enter automatically.

1. Confirm initialization in the current directory.
2. Review the proposed package name. For this local tutorial, accepting the generated default is fine.
3. When asked whether to set up tscircuit AI skills, choose **No** for the manual track.
4. Allow the project dependencies to install.

Do not use `-y` in this demonstration. `-y` skips prompts and accepts defaults, which is convenient for automation but hides the decisions we are trying to teach.

### Alternative one-command directory form

From the parent directory, the CLI can create a named directory directly:

```sh
tsci init kicad-people-demo
```

For automated environments, the shape is:

```sh
tsci init kicad-people-demo --yes
```

Be aware that `--yes` accepts current defaults for every skipped prompt. With the recording-time CLI, that includes setting up the optional tscircuit AI skills. Use the interactive path when you specifically want to decline them.

And to generate files without installing dependencies:

```sh
tsci init kicad-people-demo --yes --no-install
```

These alternatives are useful, but the interactive path is better for a first explanation.

## 52:00 — Inspect the generated project, file by file

### Narration

Initialization is not complete just because the CLI printed a success message. We are going to inspect what it created.

Start with:

```sh
pwd
ls -la
```

A current starter project contains these important authored files:

```text
.gitignore
.npmrc
index.circuit.tsx
package.json
tscircuit.config.json
tsconfig.json
```

Dependency installation may also create `bun.lock` and the `node_modules` directory. Generated build outputs such as `dist` appear later when commands create them.

### `index.circuit.tsx`

Read it without editing:

```sh
sed -n '1,200p' index.circuit.tsx
```

### Narration

This is the circuit entry file. The `.tsx` extension means TypeScript with JSX syntax. The current starter exports a function containing a board, a resistor, a capacitor, and a trace.

Do not teach the element syntax yet. Point out only the structure:

1. the file has a default export;
2. the returned JSX describes circuit elements;
3. component names such as `R1` and `C1` are explicit;
4. a trace references named component pins.

We will unpack every character of this file in Episode 2.

### `package.json`

```sh
sed -n '1,240p' package.json
```

### Narration

`package.json` is the project manifest. For a KiCad user, this is not the circuit schematic and not the PCB. It describes the software package surrounding the circuit.

Read these sections:

- `name` identifies the package;
- `version` identifies the package version;
- `scripts` gives memorable aliases such as `dev`, `build`, `snapshot`, and `typecheck`;
- `devDependencies` records tools needed to develop the circuit, including tscircuit and TypeScript.

When we run:

```sh
bun run dev
```

Bun looks up the `dev` script in this file. In the generated project that script runs `tsci dev`. The script is an alias, not a separate development server.

### `tsconfig.json`

```sh
sed -n '1,260p' tsconfig.json
```

### Narration

`tsconfig.json` configures TypeScript. A KiCad project normally does not need a programming-language compiler configuration, so this file deserves explanation.

The important values for today are:

- `strict: true`, which enables stronger type checking;
- `jsx: react-jsx`, which allows the JSX syntax used by circuit elements;
- `types: ["tscircuit"]`, which exposes tscircuit's types to the project;
- the include and exclude lists, which define which source files TypeScript examines.

Strong typing does not prove the circuit is electrically correct. It catches a different class of problems: invalid program structure, misspelled typed properties, and incompatible values.

### `tscircuit.config.json`

```sh
sed -n '1,200p' tscircuit.config.json
```

### Narration

This is project-specific tscircuit configuration. A new project may contain only a `$schema` URL. That schema allows editors and tooling to validate and suggest configuration fields. An almost-empty configuration file is not broken; it means the project is using defaults.

### `.npmrc`

```sh
sed -n '1,120p' .npmrc
```

### Narration

This file tells package tooling where the `@tsci` package scope is hosted. It is package-registry configuration. Do not put authentication tokens into a video or commit secrets casually.

### `.gitignore`

```sh
sed -n '1,240p' .gitignore
```

### Narration

`.gitignore` tells Git which generated or machine-specific paths should not be committed. Typical examples include `node_modules`, build output, environment files, editor state, and tscircuit cache data.

The principle is the same as in a disciplined KiCad repository: commit the source of truth and necessary project metadata; do not commit every local cache or generated intermediate.

### `bun.lock`

If dependency installation created `bun.lock`, explain it without printing the whole file:

```sh
ls -lh bun.lock
```

### Narration

The lockfile records the resolved dependency graph so another machine can reproduce the same package versions more reliably. Commit the lockfile. Do not hand-edit it.

### `node_modules`

```sh
du -sh node_modules
```

### Narration

`node_modules` contains installed package code. It may be large. It is restored from `package.json` and the lockfile and is normally ignored by Git. Do not review it as though it were your authored circuit source.

## 60:00 — Verify the project without designing anything

### Narration

We will finish with verification. We are not changing the circuit yet.

First confirm the local dependency state:

```sh
bun install
```

If everything is already installed, Bun should complete quickly. Running it again should be safe and should not create a different project design.

Now run the generated type-check script:

```sh
bun run typecheck
```

No output beyond a successful command is often a good result. It means TypeScript found no type errors.

Then run:

```sh
tsci doctor
tsci version --verbose
ls -la
```

The final directory listing confirms that the project files are still present after dependency installation and verification. We will cover Git repository initialization separately when version-control workflow becomes relevant.

Do not launch `tsci dev` yet. End the episode with the project fully prepared and the next command visible, but not executed:

```sh
tsci dev
```

### Final narration

We now have a working tscircuit CLI, a map of its commands, and a project whose files we actually understand.

Nothing in this setup depended on AI. We know where the circuit source lives. We know which file records dependencies. We know where TypeScript is configured. We know how project-level tscircuit configuration is represented. And we know how to ask the CLI for accurate help instead of guessing.

In Episode 2, we will open `index.circuit.tsx`, explain the starter circuit line by line, run the development server, and connect source changes to schematic, PCB, and 3D output.

Stop here. Do not tease a completed complex board. The achievement of Episode 1 is a clean, understood, reproducible starting point.
